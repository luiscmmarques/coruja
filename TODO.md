### Covers: where the missing ones actually are (investigated 2026-09-13)

The complaint was "why is it so hard to get a cover out of Google Books". Two separate causes, both verified against the live services, and neither of them fixable by calling a different API.

**The bytes are unreadable, not unavailable.** `books.google.com/books/content?…` answers with the JPEG and no `Access-Control-Allow-Origin` header at all, and 405s a preflight. The app stores covers as blobs (that is what makes the shelf draw itself offline), so a `fetch` is the only way in, and that host forbids it — permanently, from any browser, whatever the CSP says. The JSON API is fine: `www.googleapis.com` does send the header. So text arrives and pictures cannot, which is exactly the symptom. As of v1.2 the URL is not even produced (see PLAN.md); the fix is the Worker proxy above, and with it `zoom=0` instead of `zoom=1` for an image larger than the default 128×185 px thumbnail (verified 200).

**And often Google has no image either.** Of five probed French and children's ISBNs, two had a record with `imageLinks` entirely absent (9782211201957 `L'ouragan`, 9782075138659), two had thumbnails at 128×185, and one probe caught Google's transient `503 backendFailed`. Open Library is thin in the same places from the other direction: two of the same ISBNs have no record at all, though it does have covers for books Google does not. So no third provider closes this: the catalogues with permissive CORS are thin, and the ones with pictures do not do CORS.

Which makes **cover photography** (PLAN.md's "deliberately not in v1") the real answer for a French-language shelf, and much cheaper now than when it was deferred: blob storage exists in the `covers` table, the camera is already wired up for the scanner, and the missing pieces are a crop UI and a shutter. It is also the only source with 100% coverage, zero egress and no third party at all.

### Places become real things (design, 2026-09-13 — deliberately not built yet)

Today `Book.shelfLocation` is free text ("salon, top shelf"), and it shows: it is typed again for every book, it is searchable but not filterable, and two spellings of the same shelf are two different places. The ask is that a location behave like a collection — created once, picked from a list, and a filter on the shelf. Everything below is the shape; none of it is written.

**A `Location` is its own entity, not a `Collection` with a kind flag**, and the reason is cardinality, not tidiness. A physical book is in exactly one place at a time (single-select, and moving it is a replacement), while it belongs to any number of collections (multi-select, and each is independent). One table serving both would need a flag that half the code has to remember to honour, and the first place it would be forgotten is the picker. Two tables, one of which is nearly identical to the other, is the cheaper mistake. `Location { id, name, emoji, createdAt }` mirrors `Collection` exactly, `Book.locationId?: string` replaces `shelfLocation`, and the picker (`CollectionPicker.svelte`) grows a single-select mode where choosing a ✓-marked entry clears the field rather than toggling a set.

The emoji palette is a **third** vocabulary and must stay one: readers own the animals, collections own the feelings (`COLLECTION_EMOJI`, `src/lib/domain/types.ts`, whose doc comment is explicit that keeping the vocabularies apart is what makes the shelf legible), so places own places — 🛏️ 🛋️ 🎒 🚗 📚 🧺 🚪 and a handful more. A location's emoji is what appears on the card, where the 📍 and the free text sit today (`src/routes/+page.svelte:504`).

Dexie **v3** adds `locations: 'id'` in a new `version()` block — never an edit to v1 or v2 — and its `upgrade` migrates the free text: collect every distinct non-empty `shelfLocation`, fold case and trim whitespace to dedupe ("Salon" and "salon " are one shelf), create a `Location` for each in first-seen order with a neutral default emoji, point each book at its own, and leave `shelfLocation` unread thereafter. Nothing is lost, which is the only acceptable migration for a field a parent typed by hand.

The rest is the ordinary blast radius, and it is worth stating so nobody underestimates it: the `Required<T>` fixtures in `src/lib/domain/transfer.test.ts:46` stop compiling until `locationId` is in them, `parseImport` (`transfer.ts:142`) must validate the new field **and keep accepting the old one** — a backup file is the only copy of a family's shelf that survives clearing a browser, so an old export must still import, applying the same dedupe-and-create migration on the way in — the shelf gains a `<select>` next to the existing filters, Setup gains a CRUD panel like the collections one (deleting a place unthreads it from every book in one transaction; the books stay), and five i18n catalogues gain the labels. Plus PLAN.md's "inventory half" paragraph, which currently describes the free text as a feature.

**Where this collides with borrowed books:** "on the shelf in the salon" and "borrowed from the Médiathèque Valais – Martigny" both answer "where is this book", and it is tempting to make the library one more Location. That would be wrong — a library book has a _lender_ and possibly a return date, which a shelf in the salon never has, and a returned library book must not silently become a book the household owns. See the borrowed-books design below for the joint model.

### Borrowed from the library (design, 2026-09-13 — deliberately not built yet)

The case is the Médiathèque: a stack comes home, gets read, goes back. Today those books look owned, which is the one claim the inventory half makes, and "return by" has nowhere to live.

**Four optional fields on `Book`, and no `Loan` table.** `borrowed?: boolean`, `borrowedFrom?: string`, `dueOn?: string` (YYYY-MM-DD) and `returnedOn?: string`, plus `Settings.loanDays?: number` remembering the last loan's length so the next due date is a prefilled value to accept rather than a sum to do. Absent `borrowed` means the family owns it, which is what makes this free: "books we own" becomes a computed `!borrowed`, every existing row is already correct, and the repo's own convention (`adult?`, `archived?`, `editedByHand?`, the `lookupEnabled` rule) is followed rather than a new enum invented that would force a whole-table rewrite to say "owned" out loud. `returnedOn` is a date rather than a third ownership state because "returned" is not a kind of ownership; the three states a UI needs — ours, out, back at the library — derive from the pair in one pure function, which cannot contradict itself the way a stored third state can.

The cardinality question is whether loan _history_ matters, and the answer is no. A favourite comes home from the médiathèque three summers running, but the app already funnels a re-scanned ISBN into the existing row (`findBookByIsbn`, and the Scan screen's duplicate branch), so a re-borrow clears `returnedOn`, sets a new `dueOn`, and the previous loan's dates are simply gone. Nothing reads them: the ladder, the badges, the page totals, the year count and "her longest book" all hang off `Reading` rows, which are insert-only per re-read and untouched by every one of these transitions. A `Loan` table would buy the sentence "we had this out in March 2025" and cost a Dexie table, an eighth array in the backup envelope, a validator, a `Required<Loan>` fixture, a cascade in `deleteBook`, a tombstone question for Plus, and a history screen nobody asked for.

**There is no Dexie migration, and that is the correct answer, not an oversight.** IndexedDB stores whole objects; adding optional properties is not a schema change, and the schema in Dexie _is_ the index list. No new index is needed because every shelf filter is in-memory — the exact reasoning already written into the v2 block's comment about `collectionIds`. Two things to say out loud so nobody adds one anyway: do not index `borrowed`, because booleans are not valid IndexedDB keys and the index would silently contain nothing (the existing `archived` entry in `books: 'id, isbn13, title, archived'` is already that latent no-op and deserves a comment), and do not write an `upgrade()` that stamps `borrowed: false` across the table, because it rewrites every row to destroy the absent-means-owned invariant that makes this free.

**Returning a book must not cost a child anything, and the danger is plumbing rather than intent.** The shelf's book array feeds both the list and `pagesRead`/`longestFinished`, so a "returned books are hidden" filter applied one line too early silently subtracts pages she really read and can erase her longest book — decay, invisibly, which guardrail #2 forbids. The ownership predicate therefore belongs _inside_ the visible-books filter beside status and language, never in the array the stats read. `deleteBook` cascades into readings, so any "tidy up what went back" affordance is a history shredder with a housekeeping label: rejected permanently. `bookStatus` and `finishedBookCount` read readings and never books, so a returned book a child finished still reports finished and the ladder cannot move; `settleBadges` must keep receiving the unfiltered table, so Doorstop on a 500-page library book survives the return, as it must, badges being insert-only. Two figures _should_ change, though, because they are about objects in the house: the shelf's own count, and `shelfReadPercent`, whose denominator would otherwise sink a little every time the family used the library — a progress number decaying because of good behaviour. Fix that at the call site by passing the owned subset, not by adding a parameter to the pure function. And returning needs no confirmation dialogue, unlike deleting: nothing is lost.

**A new pure module, `src/lib/domain/loans.ts`**, importing only `./types.ts`: `loanState(book)`, `isInTheHouse(book)` / `booksInTheHouse(books)` / `ownedBooks(books)`, `daysUntilDue(book, todayIso)`, `dueTone(book, todayIso)`, `dueDateFrom(startIso, days)`, `loanDaysFor(settings)` with `DEFAULT_LOAN_DAYS = 28`, and a `byDueDate` comparator. Today arrives as a `YYYY-MM-DD` string, not as milliseconds: `retry.ts` takes milliseconds because it measures instants, while a due date is a calendar day printed on a receipt, and comparing a day against an instant is how you get "due tomorrow" in Zurich and "due today" in Lisbon for the same book. Internally the arithmetic goes through `Date.UTC` at midday, the trick `recordPastRead` already uses for exactly this reason. Every ambiguous input fails into silence: no `dueOn`, an unparseable `dueOn`, a `returnedOn` already set, or `dueOn` present while `borrowed` is absent all render nothing, because the cost of failing the other way is telling a family a book is late when it is not.

**"Overdue" does not exist.** The past case is one blameless phrase with no number in it — _still out_ — because a number that grows is a scoreboard of failure, and the person reading it already knows. The future cases are plain facts in the muted meta line: _back by 3 October_, _back in 3 days_, _back tomorrow_, _back today_. `--alert` is forbidden on every loan surface; `--ink-soft`, and at most the `--gold` the app already uses for a boast. The line, stated so it can be defended later: **the app may state the fact where the book is, and let you filter and sort by it; it may not initiate.** No notification, no banner on open, no count on the bottom nav, no toast, no sort-to-top by default, and nothing withheld because a date passed. If reminders are ever genuinely wanted, the sanctioned mechanism is the generated `.ics` PLAN.md already names — and a library return is the one obligation in this app that belongs to the parent rather than the child, which is what would make it legitimate.

**The feature is won or lost on the Scan screen**, because a stack of eight books comes home at once and nobody will open the edit dialogue eight times. So: a session toggle above the viewfinder — _"Everything I scan now is from the library"_ — held in page state and deliberately **not** persisted, because a remembered mode silently mislabels next month's bookshop haul, and a wrongly-borrowed book is worse than an unlabelled one. While it is on, the save path passes `borrowed`, the remembered library name and a prefilled `dueOn`, and the confirmation card says what it recorded so a mistake is visible immediately. Elsewhere: one more `·` item on the card's meta line, one new filter `<select>` defaulting to "in the house" and rendered only when something is actually borrowed (the same "a filter with one option is furniture" rule the language filter follows), an opt-in "Back soonest" sort, a _Back to the library_ button in the card actions — which needs `flex-wrap` on that row, since it is a fourth control on a 375 px card — and a loan block in the edit dialogue's advanced drawer with a `<datalist>` of library names already on the shelf, so the second book inherits the first one's spelling. Setup gains nothing, and that is deliberate: every control there is five translations and a permanent surface, and this feature earns none.

**Loan writes must not go through `editBook`**, which stamps `editedByHand` and thereby blocks re-enrichment forever. Whose book this is and when it goes back is not a metadata correction, and a family that ticks "from the library" must not thereby forfeit the cover a lookup would have fetched. So a small `setLoan` / `returnBook` / `borrowAgain` trio in the db layer that patches without the flag. (`toggleBookCollection` already burns `editedByHand` for filing a book in a collection — precedent, but the wrong one; do not extend it.)

Backup: `buildExport` needs no change, the envelope version stays 1, four `isOptionalString`/`isOptionalBoolean` clauses join `isBookShape`, `loanDays` joins the settings shape, and the dates are validated as strings only — `parseImport` rejects rather than repairs, and a date-shape check would reject a whole shelf over one typo in a field whose worst failure mode is already silence. The `Required<T>` fixtures stop compiling until all four fields are present, which is the discipline working; the library name in them **must be invented**, for the same reason the fixture reader is called Inês.

**The library stays free text, with a `<datalist>`.** A household with one or two libraries gets canonical spelling after typing the name once and pays nothing — no table, no Setup section, no backup array, no unthread-on-delete transaction, no Plus tombstone question. The one thing an entity would genuinely add, a lending period to hang the due date on, is delivered instead by remembering the last loan length. Promote it to a `Library` entity only when a household juggling three lenders with three periods actually exists; the free text becomes the seed for the names, exactly as `shelfLocation` is being promoted now.

Not building, with the reasons: **no library APIs** (not SRU, not Z39.50, not RERO/SLSP, not Netbiblio) — a second network egress in an app whose strongest privacy sentence is that there is exactly one, needing the CSP opened to a host that identifies the family's town, and every such interface is per-institution, so it works for one family and rots when the médiathèque changes vendor. **No library account, card number or PIN** — real PII with real consequences, in an app that deliberately stores no birthdate. **No due-date sync, no renewals, no reconciliation** — the library's system is the source of truth and coruja is a note about it; a note that claims to be synchronised and is not is worse than a note. **No fine estimates, no lateness counters, no "returned on time" statistics** — the first is a streak under another name and the last is a scoreboard of a family's worst weeks. **No return-a-stack screen** — eight books going back is eight taps down a filtered list.

**The crux, against the places design above: these are two axes, not one.** The decisive case is the ordinary one — a borrowed book that is in the house has both, it is the library's _and_ it is on the bedside table, and one field cannot hold both. The moment a family tries, the more useful of the two loses, because the whole purpose of the places list is "walk over there and put it back", and a place you cannot walk to inside your own home poisons it. A returned book is the second test: it is at the library, so it has no place in the house at all, yet last week's `shelfLocation` is still in the row. So: **a place answers "where is the object", one per book, meaningful only while it is here; the loan answers "whose is it and when must it go back", meaningful whether it is here or not.** Four honest combinations, all of which occur. Two contracts where the designs touch, to be written into whichever ships second: a place's book count and the place filter must run over `booksInTheHouse`, or "salon, top shelf" lists three books that are at the médiathèque; and a returned book **keeps** its `shelfLocation`, because the same book borrowed again will live in the same spot and clearing it would lose information to fix a display problem the first contract already fixes. Share the machinery — the picker, the Setup list pattern, the delete-and-unthread helper — but never a `kind: 'shelf' | 'library'` column on one table, which would force every filter and count to filter by kind forever.

One boundary, because PLAN.md's v1 exclusion list says "lending" and this reverses part of it: **borrowing _in_** — the library's book in our house — is an ownership fact and is what this design adds; **lending _out_** — our book at a friend's house — is a place fact ("where is it? at Léa's"), belongs to the places design, and stays out of scope. Naming the split is what stops the reversal from being read as "lending is in now".

Guardrails, walked: nothing here is a streak, as long as nobody adds "returned on time, six loans running" — the most natural bad idea this feature invites, hereby rejected. Nothing can decay if the ownership filter stays out of the stats array and returned books are never auto-deleted. No badge can be revoked, `settleBadges` seeing the whole table. No comparison between readers; a due date is a household fact. Nothing expires or is withheld when a date passes, which is the difference between a fact and a deadline. No nagging, per the line drawn above. No red. One judgement call flagged rather than decided: a 🏛️ badge for finishing a library book would be insert-only, structurally identical to Cataloguer, and unloseable — but it costs a `BadgeId`, a label and a description in five catalogues, so it belongs to whoever owns the catalogue's size. What must never exist is any badge or count keyed on returning _punctually_.

Order of work, roughly nine files and ~450 lines of which a quarter is translation — the same weight as collections: the pure module and its tests first, alone; then the type fields (this is the commit that breaks `transfer.test.ts`, on purpose); then the transfer validators and fixtures; then the db trio; then the i18n keys, the largest mechanical chunk; then the shelf, which needs the most care; then Scan; then the two lines on the badges page that keep the page total and the read-percentage honest, which is the guardrail fix nobody would think to look for; then the docs the pre-commit hook will demand anyway.

## Coruja Plus (plus.coruja.app): feasibility evaluation, 2026-09-07

A paid sibling with cloud profile storage and extra features, in its own repo, taking free-app features by backport. Evaluated against the code as it ships in v1.

**Verdict: well-positioned, with three cheap preparations worth doing before the fork.**

### What the current architecture already gets right

- **The domain layer is dependency-free** (verified: zero impure imports). Ladder, badges, stats, ISBN, transfer, pin: all of it is shared logic both apps import unchanged. This is the backport currency.
- **Every UI data access goes through `$lib/db`'s exported functions** (verified: zero components import Dexie or touch IndexedDB; the one raw-handle leak in scan was closed during this evaluation with `getBook`). The db module's export list IS the storage interface: ~25 functions. Plus wraps or decorates exactly this seam with a sync engine; nothing above it needs to know.
- **Readings and badges are insert-only by design** (guardrail #3). Append-only logs are the easy case in sync: no conflicts, just union. The hard 20% is confined to the mutable tables (books, readers, collections) and to the few hard deletes.
- **The backup file is a versioned, validated, upgrade-contract-tested wire format.** A first Plus release can sync by shipping this exact envelope to the cloud: crude (whole-profile, last-writer-wins) but correct, private, and already tested.
- **CSP divergence is one config list**: Plus adds `https://api.coruja.app` to `connect-src` in vite.config and nothing else changes.

### Prepare before forking (cheap now, expensive after divergence)

- [ ] **Tombstones instead of hard deletes** for books and collections (`deletedAt` field, filtered everywhere, purged after N days). Without this, a deletion on one device resurrects on the next sync. This is the single biggest sync enabler and is also harmless in the free app. `undoLatestReading` needs the same treatment or an explicit "retraction" event.
- [ ] **Split Settings into device-local vs profile** (locale and activeReaderId are device-local; adultPinHash and lookupEnabled are profile). One interface with two halves; free app stores both locally, Plus syncs only the profile half.
- [ ] **Add `updatedAt` to mutable records** (books, readers, collections), stamped in editBook/editReader/editCollection. Free app ignores it; last-write-wins sync depends on it. Backup format carries it as another optional field: the upgrade contract already proves old files stay importable.

### What Plus builds that free never carries

Account + auth, the sync engine behind the `$lib/db` interface, api.coruja.app, payment. Strongly consider end-to-end encryption of the synced blob: the free app's privacy promise is "no server, nothing leaves"; the Plus promise should be "a server it cannot read", or the brand's privacy story splits in two.

### Repo strategy

Two repos, free as upstream: Plus is a fork carrying `coruja` as a git remote, and backporting is `git merge upstream/main` (single-commit history and the discipline below keep merges clean), not cherry-pick archaeology. Discipline that makes it work: Plus-only code lives in new modules (`src/lib/plus/`), and Plus touches existing files only at the named seams (db interface, vite.config CSP, one account card in Setup, one header affordance). Every shared-file edit belongs upstream in the free app first.

### Licensing note (decide before accepting outside contributions)

The free app is AGPL. As sole copyright holder you can dual-license your own code into a proprietary Plus freely. That freedom ends the day an external contribution is merged without a CLA: from then on, that contributor's AGPL terms bind Plus too. Either take a lightweight CLA from day one, or keep Plus's use of the free codebase at arm's length (only code you authored).

### Guardrails check

Cloud storage does not violate "nothing is shared outward" if it stays a private family profile: sync is the same family on more devices, not an audience. The guardrails travel with the domain layer into Plus unchanged. plus.coruja.app needs its own privacy page; the free app's stays exactly as strict as it is.

## Rejected

- **Movies and other media inside coruja.** Rejected 2026-09. Not for the code — `Book`→`Item` is two days — but for three compounding reasons: the mark _is_ a book (asymmetric V = open book, rings = pages; the identity becomes decoration); movie lookup breaks the keyless zero-config model (TMDB/OMDb need keys, and a DVD's EAN maps to a retail SKU, not a canonical film); and decisively, **the mission inverts** — coruja's gamification exists to make a child want to read more, and the same ladder applied to films rewards screen time, the thing parents of an eight-year-old are trying to limit. A badge for twenty movies is an anti-feature wearing the same clothes. If a household media inventory is ever wanted, it is a **sibling app** with its own name and mark and _no gamification_ — the Graftful→coruja pattern, not a stretched brand.
- **Client-side analytics.** The CSP blocks third-party scripts by design and the privacy page says "no analytics script" plainly. Usage is read from Cloudflare's edge-side request counts, which exist anyway. Do not enable Cloudflare _Web Analytics_ specifically — it injects a beacon.
- **Streaks, XP decay, time-limited events, reading reminders.** PLAN.md guardrails; listed here so a search for a rejected feature lands somewhere.
- **Open Library `subjects` as genre data.** Noisy, unbounded, English-only regardless of the book's own language.
